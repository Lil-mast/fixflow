# FixFlow Data Model

**Status:** design baseline for the weekend build. The tables are not created at this
commit. `infrastructure/template.yaml` will be the source of truth for keys, indexes, and
capacity settings.

Related documents:

- [Architecture](architecture.md)
- [API contract](api.md)

## 1. Design rules

1. **Access patterns first.** Every index exists because a documented query needs it. Do not add an index "just in case."
2. **One item per report.** The report item is the current state. History lives in an append-only events table.
3. **Transactions for state changes.** A status update and its event are written together. If either fails, neither is visible.
4. **Conditional writes for safety.** Create uses `attribute_not_exists(reportId)`. Transitions use `status` and `version` conditions.
5. **No PII in indexes.** Projections include operational fields only. Descriptions, coordinates, and evidence keys stay in the base item.
6. **Timestamps are sortable strings.** Store ISO 8601 UTC with milliseconds and `Z` so lexicographic order matches time order.
7. **Tokens are short-lived.** Workflow task tokens are stored separately with TTL and are never projected or logged.

## 2. Tables at a glance

| Table | Purpose | Billing | PITR | TTL |
| --- | --- | --- | --- | --- |
| `FixFlowReports` | Current report state and query indexes. | On-demand | On | No |
| `FixFlowReportEvents` | Append-only audit history. | On-demand | On | No (retain, or add a policy later) |
| `FixFlowWorkflowTokens` | Step Functions task tokens. | On-demand | Off | `expiresAt` |

The PDF proposed two tables. A third internal table is deliberate: task tokens are bearer
capabilities, and keeping them out of report records removes an entire class of accidental
exposure through admin responses, GSIs, exports, or logs.

## 3. `FixFlowReports`

### Keys

| Key | Attribute | Type | Example |
| --- | --- | --- | --- |
| Partition key | `reportId` | String | `e3b0c442-98fc-4c14-9afb-f4c8996fb924` |
| Sort key | none | - | - |

`reportId` is a UUIDv4 generated by the browser once per submission. It is both the primary
key and the idempotency key. The server validates the format and refuses to overwrite an
existing item.

### Status values

| Status | Meaning | Terminal |
| --- | --- | --- |
| `SUBMITTED` | Report received. | No |
| `VALIDATING` | Required fields and evidence are being checked. | No |
| `VALIDATION_FAILED` | System validation failed. The resident may submit a new report. | Yes |
| `REVIEW_PENDING` | Awaiting administrator review. | No |
| `NEEDS_INFO` | The resident must provide more information. | No |
| `REJECTED` | An administrator rejected the report. | Yes |
| `APPROVED` | Accepted for action, not yet assigned. | No |
| `IN_PROGRESS` | Assigned to a team and being worked on. | No |
| `RESOLUTION_PENDING` | Completion evidence submitted, awaiting verification. | No |
| `RESOLVED` | Resolution verified by an administrator. | Yes |
| `REVIEW_EXPIRED` | The review window elapsed, but an administrator can still decide. | No |

`REVIEW_EXPIRED` is intentionally not terminal. The workflow issues a fresh review token
after the timeout, and the decision endpoint accepts a decision from either
`REVIEW_PENDING` or `REVIEW_EXPIRED`.

A report that reaches review normally has `version = 3`: submission is version 1,
`SUBMITTED -> VALIDATING` is version 2, and `VALIDATING -> REVIEW_PENDING` is version 3.
Priority calculation updates the score without incrementing the version because it is not a
lifecycle transition.

### Indexes and access patterns

| ID | Access pattern | Index | Keys | Projection |
| --- | --- | --- | --- | --- |
| AP1 | Get a report by internal ID | Base table | `reportId` | All |
| AP2 | Create a report idempotently | Base table | `reportId` + `attribute_not_exists` | - |
| AP3 | Update status and version | Base table | `reportId` + `status` + `version` condition | - |
| AP4 | List reports by status, newest first | `GSI1` | `GSI1PK = STATUS#<status>`, scan `GSI1SK` descending | INCLUDE operational fields |
| AP5 | List all reports, newest first | `GSI3` | `GSI3PK = ALL`, scan `GSI3SK` descending | INCLUDE operational fields |
| AP6 | Resolve a public reference | `GSI2` | `GSI2PK = PUBLIC#<publicRef>` | KEYS_ONLY, then `GetItem` |
| AP7 | Read a report's event history | Events table | `reportId`, sort `eventId` ascending | All |
| AP8 | Read the public timeline | Events table | `reportId`, filter `visibility = PUBLIC` | All, then map |
| AP9 | Load a workflow token | Tokens table | `reportId` + `taskType` | All |
| AP10 | Count reports by status | `GSI1` | `Select = COUNT` per status | - |
| AP11 | Compute averages | `GSI3` | Page all reports, filter `dataSource = LIVE` | - |

**GSI1 - status index**

```text
Partition key: GSI1PK = STATUS#<status>
Sort key:      GSI1SK = <createdAt>#<reportId>
Projection:    INCLUDE reportId, publicRef, category, area, status, priority,
                        assignedTeam, createdAt, updatedAt, dataSource
```

Every transition updates `GSI1PK` to the new status. `GSI1SK` stays
`<createdAt>#<reportId>`, so the report appears in the new status partition immediately and
disappears from the old one. `transition_report` is the only writer that changes these keys.

**GSI2 - public reference index**

```text
Partition key: GSI2PK = PUBLIC#<publicRef>
Sort key:      GSI2SK = REPORT
Projection:    KEYS_ONLY
```

The public endpoint does one index query to resolve the reference and one `GetItem` for
the current record. It then maps an explicit public projection. It never returns the raw
item.

GSIs are eventually consistent. A resident who opens the tracking page in the same second
as submission can see a temporary `404`. The tracking page should retry for up to 5
seconds before showing "not found". If strict read-after-write is required later, add a
`FixFlowPublicRefs` mapping table with `publicRef` as its partition key and write it in the
same transaction as the report; do not add a scan as a fallback.

**GSI3 - all reports index**

```text
Partition key: GSI3PK = ALL
Sort key:      GSI3SK = <createdAt>#<reportId>
Projection:    INCLUDE reportId, publicRef, category, area, status, priority,
                        assignedTeam, createdAt, updatedAt, dataSource
```

`GSI3` gives the admin dashboard a single "newest first" query without scanning. The
cardinality is fine for a demo and for the expected early volume. If the application grows
to many organizations, replace `ALL` with `ORG#<orgId>` and add the tenant to the key.

**Category filtering:** the MVP filters `category` on the returned page. Adding a fourth
index for category is not justified at demo volume. If category filtering becomes a
primary access pattern, add `GSI4PK = CATEGORY#<category>` with the same sort key.

### Capacity and cost

- On-demand capacity. No provisioned throughput to tune or forget.
- Each transition writes two items in a transaction (report + event), which costs roughly
  twice the write units of a single put. At demo volume this is negligible.
- Each GSI doubles write cost for projected attributes. Three indexes are acceptable here;
  a fourth would need a measured reason.
- Enable point-in-time recovery on `FixFlowReports` and `FixFlowReportEvents`. The demo
  data is small and recovery is cheap.

## 4. `FixFlowReportEvents`

### Keys

| Key | Attribute | Type | Example |
| --- | --- | --- | --- |
| Partition key | `reportId` | String | `e3b0c442-98fc-4c14-9afb-f4c8996fb924` |
| Sort key | `eventId` | String | `01J8Z3Y6Q7K5M2N4P6R8S0T2V4` |

`eventId` is a ULID: lexicographically sortable by time, with 80 bits of randomness. It
gives a stable order even when two events share a millisecond.

### Attributes

| Attribute | Type | Required | Purpose |
| --- | --- | --- | --- |
| `reportId` | String | Yes | Partition key. |
| `eventId` | String | Yes | ULID sort key. |
| `actorType` | String enum | Yes | `RESIDENT`, `ADMIN`, `SYSTEM`, `TEAM`. |
| `actorId` | String | Yes | Cognito `sub` for admins, `SYSTEM` for workflow steps, `RESIDENT` for the public submitter. Never public. |
| `action` | String enum | Yes | Event action. See the list below. |
| `previousStatus` | String enum | No | Null for the first event. |
| `newStatus` | String enum | Yes | Status after the action. |
| `timestamp` | String timestamp | Yes | Event time. Matches `eventId` ordering. |
| `visibility` | String enum | Yes | `PUBLIC` or `ADMIN`. Default `ADMIN`. |
| `publicMessage` | String | No | Safe message for the public timeline. Max 280 characters. |
| `comment` | String | No | Admin-only note or reason. Max 2,000 characters. Never public. |
| `metadata` | Map | No | Small structured context: reason code, team label, score, message hash. No PII, no tokens, no evidence keys. |

### Event actions

| Action | Typical actor | Public by default |
| --- | --- | --- |
| `REPORT_SUBMITTED` | Resident | Yes |
| `VALIDATION_STARTED` | System | No |
| `VALIDATION_FAILED` | System | No |
| `PRIORITY_CALCULATED` | System | No (the priority is on the report; the event is operational) |
| `REVIEW_REQUESTED` | System | No |
| `REVIEW_APPROVED` | Admin | Yes, with a curated `publicMessage` |
| `REVIEW_REJECTED` | Admin | Yes, with a generic `publicMessage`; the reason stays admin-only |
| `INFO_REQUESTED` | Admin | Yes, with a curated `publicMessage` |
| `CLARIFICATION_PROVIDED` | Resident | Yes |
| `REVIEW_EXPIRED` | System | No |
| `TEAM_ASSIGNED` | Admin | Yes |
| `RESOLUTION_SUBMITTED` | Admin | Yes |
| `RESOLUTION_VERIFIED` | Admin | Yes |
| `RESOLUTION_REJECTED` | Admin | Yes, with a generic message |
| `WORKFLOW_FAILED` | System | No |

Public timeline rule: an event is visible only when `visibility = PUBLIC` **and**
`publicMessage` is present. The handler that writes the event decides visibility; the
public read path does not infer it from `action`.

The raw resident clarification text is stored in `comment` (admin-only). The public
`CLARIFICATION_PROVIDED` event uses a generic `publicMessage` such as "Resident provided
additional information." Do not copy resident text into `publicMessage`.

When `transition_report` writes a `PUBLIC` event with a `publicMessage`, it also sets the
report's `publicSummary` in the same transaction. The public lookup then needs one
`GetItem` and does not have to query the event history for the latest message.

### Append-only enforcement

- Lambda roles are granted `dynamodb:PutItem` on the events table, not `UpdateItem` or
  `DeleteItem`.
- Add an explicit IAM deny for `dynamodb:UpdateItem` and `dynamodb:DeleteItem` on the
  events table and its indexes. This is defense in depth beyond the absence of a grant.
- The only write path is `transition_report`, which writes the event inside the same
  transaction as the report update.

## 5. `FixFlowWorkflowTokens`

### Keys

| Key | Attribute | Type | Example |
| --- | --- | --- | --- |
| Partition key | `reportId` | String | `e3b0c442-98fc-4c14-9afb-f4c8996fb924` |
| Sort key | `taskType` | String | `REVIEW` |

`taskType` is one of `REVIEW`, `ASSIGNMENT`, `RESOLUTION`, or `VERIFICATION`. A report has
at most one active token per task type. Clarification does not use a long-lived token: the
workflow ends at `NEEDS_INFO`, and a resident response starts a new review execution.

### Attributes

| Attribute | Type | Required | Purpose |
| --- | --- | --- | --- |
| `reportId` | String | Yes | Partition key. |
| `taskType` | String enum | Yes | Sort key. |
| `taskToken` | String | Yes | Step Functions task token. Sensitive. Never logged or returned. |
| `executionArn` | String | Yes | Execution that owns the token. |
| `status` | String enum | Yes | `PENDING`, `CONSUMED`, or `EXPIRED`. |
| `createdAt` | String timestamp | Yes | Token creation time. |
| `expiresAt` | Number (epoch seconds) | Yes | DynamoDB TTL attribute. |
| `consumedAt` | String timestamp | No | When the callback consumed the token. |
| `consumedBy` | String | No | Cognito `sub`, `SYSTEM`, or `RESIDENT`. |
| `taskVersion` | Number | Yes | Conditional update guard against double consumption. |

### Rules

- `expiresAt` = wait timeout + 1 day. Review tokens: 72 hours + 1 day. Later tokens: 14 days + 1 day.
- The callback handler performs a conditional update `status = PENDING AND taskVersion = :v` to `CONSUMED`, then calls `SendTaskSuccess`.
- If `SendTaskSuccess` returns `TaskTimedOut` or `InvalidToken`, record an expired state and return a conflict. Do not retry indefinitely.
- The token record is deleted by TTL after it is no longer useful. Do not rely on TTL for immediate security; the Step Functions task timeout is the real expiry.
- Only the workflow Lambdas and callback Lambdas have read access. Admin read APIs never query this table.

### Example token item

```json
{
  "reportId": "e3b0c442-98fc-4c14-9afb-f4c8996fb924",
  "taskType": "REVIEW",
  "taskToken": "<opaque task token>",
  "executionArn": "arn:aws:states:<region>:<account>:execution:fixflow-report-workflow:e3b0c442-98fc-4c14-9afb-f4c8996fb924",
  "status": "PENDING",
  "taskVersion": 1,
  "createdAt": "2026-11-14T18:31:00.000Z",
  "expiresAt": 1795026660
}
```

## 6. S3 layout

### `FixFlowWeb`

```text
index.html
assets/<hashed-asset-files>
```

- Private bucket. CloudFront reads it through Origin Access Control.
- Block all public access.
- `index.html`: `Cache-Control: no-cache`.
- `assets/*`: `Cache-Control: public, max-age=31536000, immutable`.
- Versioning enabled for recovery.
- No directory listing.

### `FixFlowEvidence`

```text
incoming/<reportId>/<uploadId>.<ext>
incoming/resolution/<reportId>/<uploadId>.<ext>
evidence/<reportId>/<uploadId>.<ext>
resolution/<reportId>/<uploadId>.<ext>
```

| Prefix | Purpose | Lifecycle |
| --- | --- | --- |
| `incoming/` | Presigned upload target for report evidence. | Expire after 1 day. |
| `incoming/resolution/` | Presigned upload target for resolution evidence. | Expire after 1 day. |
| `evidence/` | Validated report evidence. | Retain until stack deletion or a documented 30-day retention policy. |
| `resolution/` | Validated resolution evidence. | Same. |

**Object metadata** (set by the presigned POST conditions):

| Metadata | Value |
| --- | --- |
| `x-amz-meta-report-id` | The report UUID. |
| `x-amz-meta-upload-id` | The upload UUID. |
| `x-amz-meta-purpose` | `report` or `resolution`. |
| `Content-Type` | `image/jpeg`, `image/png`, or `image/webp`. |

**Presigned POST conditions:**

- Exact `key`.
- `Content-Type` equals the declared type.
- `content-length-range` from 1 byte to 10 MiB.
- `x-amz-meta-report-id` equals the report ID.
- `x-amz-meta-upload-id` equals the upload ID.
- `x-amz-meta-purpose` equals the declared purpose.

**Server-side encryption:** SSE-S3 (`AES256`) for the weekend. SSE-KMS is a later
hardening step if key rotation and audit requirements justify the extra cost and
complexity.

**Versioning:** enabled. Abandoned `incoming/` objects expire in one day. Noncurrent
evidence versions can expire after 30 days to control storage.

**Public access:** blocked at the bucket level. There is no public object URL. Admin reads
use a 5-minute presigned GET. Public users never receive evidence URLs.

**CORS:** allow `POST` from the exact CloudFront origin and `http://localhost:5173` in
development; allow `Content-Type` and the `x-amz-meta-*` headers; expose `ETag`.

## 7. Identifier formats

| Identifier | Format | Entropy | Notes |
| --- | --- | --- | --- |
| `reportId` | UUIDv4 | 122 bits | Client-generated, used as idempotency key. Validate with a strict UUID parser. |
| `publicRef` | `FF-XXXX-XXXX-XXXX-XXXX` | 80 bits | Crockford Base32, uppercase, hyphens optional on input. Normalize before lookup. |
| `eventId` | ULID, 26 characters | 80 bits random | Sortable by time. |
| `uploadId` | UUIDv4 | 122 bits | Bound to the S3 object metadata. |
| `requestHash` | SHA-256 hex, 64 characters | - | Canonical JSON of the create request. |

`publicRef` is a capability, not a secret in the cryptographic sense. 80 bits makes
guessing impractical; rate limiting and generic `404` responses cover the rest.

## 8. Priority rules

Priority is a deterministic suggestion. It is not a safety assessment, and an
administrator can still reject, deprioritize, or escalate during review.

### Score

```text
priorityScore = severityWeight + categoryWeight
```

| Severity | Weight |
| --- | --- |
| `CRITICAL` | 40 |
| `HIGH` | 30 |
| `MEDIUM` | 15 |
| `LOW` | 5 |

| Category | Weight |
| --- | --- |
| `WATER_LEAK` | 30 |
| `DRAINAGE` | 25 |
| `POTHOLE` | 20 |
| `STREETLIGHT` | 15 |
| `WASTE` | 10 |
| `OTHER` | 5 |

### Bands

| Score | Priority | Label |
| --- | --- | --- |
| 60-100 | `P1_URGENT` | Urgent |
| 40-59 | `P2_HIGH` | High |
| 20-39 | `P3_NORMAL` | Normal |

## 9. Metrics

| Metric | Source | Definition |
| --- | --- | --- |
| Total reports | `GSI3` count | All reports with `dataSource = LIVE` unless `includeDemo=true`. |
| Awaiting review | `GSI1` count | `REVIEW_PENDING` + `REVIEW_EXPIRED`. |
| Assigned | `GSI1` count | `IN_PROGRESS`. |
| Resolved | `GSI1` count | `RESOLVED`. |
| Average submission to review | Report fields | `avg(reviewedAt - createdAt)` for reports with `reviewedAt`. |
| Average approval to resolution | Report fields | `avg(resolvedAt - approvedAt)` for reports with both. |

The MVP computes averages by paging `GSI3`. At demo volume this is fine. If the data grows,
move the aggregates to a small metrics table updated from DynamoDB Streams, or precompute
them on a schedule. Do not add that complexity this weekend.

Status counts use `FilterExpression dataSource = LIVE` unless demo mode is on. DynamoDB
still reads the filtered items for a `COUNT`, which is acceptable at demo volume. A
production design would separate demo and live data into different partitions or tables.

## 10. Demo data

- Seed records use deterministic UUIDs so the seed script is idempotent. The script uses
  conditional puts and does not overwrite a record that already exists.
- Every seed record has `dataSource = DEMO`.
- The admin dashboard shows a "Demo data" badge whenever any demo record is on screen.
- Metrics exclude demo records by default. The toggle to include them is explicit.
- Seed descriptions and locations are fictional. Do not use real resident data.
- The public tracking page for a demo record also shows a demo badge, so a viewer cannot
  mistake it for a real community outcome.

## 11. Retention and privacy

- **No contact data by default.** The MVP collects no name, email, or phone number. If a
  future version adds contact data, store it in a separate attribute, never project it to
  a GSI, and never return it from a public route.
- **Description** may contain PII. It is stored in the base item only. It is not projected
  to `GSI1` or `GSI3`, and it is not returned publicly.
- **Coordinates** are stored in the `location` map only. They are not projected or
  returned publicly. The public projection uses `area`.
- **Evidence keys** are private. The public API never returns them. Admin reads receive a
  short-lived presigned URL instead.
- **Events** are append-only. Admin comments are `visibility = ADMIN`. Public messages are
  curated and length-limited.
- **Retention:** for the challenge, delete the stack after judging. Export any audit data
  you want to keep first. A production policy would define retention per data class; the
  docs recommend 30 days for evidence and 90 days for events as a starting point, subject
  to the organization's policy.

## 12. Schema evolution

- SAM creates the tables. There is no migration framework for the weekend.
- Add new attributes with defaults; readers must tolerate missing optional attributes.
- Do not rename keys or change index keys without a backfill and a new index.
- Version the API before external clients depend on the schema.
- Keep `requestHash` stable. Changing the canonicalization invalidates idempotency for
  in-flight retries.
